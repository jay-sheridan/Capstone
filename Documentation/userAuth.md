Authentication API

This document describes the authentication REST API provided by the backend.

Base path: /api/v1/auth

Endpoints
---------

1) Register a new user

- URL
  POST /api/v1/auth/register

- Content-Type
  application/json

- Request body (JSON) — `RegistrationRequest`
  - fullName: string (required) — Full name of the user. @NotBlank
  - email: string (required) — Must be a valid email format. @NotBlank, @Email
  - password: string (required) — Minimum 6 characters; must contain at least one uppercase letter and one number. @NotBlank, @Size(min=6), @Pattern("^(?=.*[A-Z])(?=.*[0-9]).{6,}$")
  - phone: string (required) — Exactly 10 digits. @NotBlank, @Pattern("^[0-9]{10}$")

- Success response
  - HTTP 200 OK
  - Body: `AuthenticationResponse`
    {
      "token": "<jwt-token-string>"
    }

  The returned token is a JWT used to authenticate subsequent requests (include as `Authorization: Bearer <token>`).

- Error responses
  - HTTP 400 Bad Request — Validation failure
    Body: `ValidationErrorResponse`
    {
      "timestamp": "2026-03-17T12:34:56.789",
      "status": 400,
      "errorType": "VALIDATION_ERROR",
      "message": "Request validation failed",
      "missingRequiredFields": ["email","password"],
      "fieldErrors": {
        "password": ["Password must be at least 6 characters","Password must contain at least one uppercase letter and one number"],
        "phone": ["Phone must be 10 digits"]
      }
    }

    Notes: The `missingRequiredFields` array contains field names detected as missing or blank. `fieldErrors` maps field names to a list of validation messages.

  - HTTP 409 Conflict — Account already exists
    Body: `ErrorResponse`
    {
      "message": "Account already exists!",
      "status": 409,
      "timestamp": "2026-03-17T12:34:56.789",
      "errorType": "AccountAlreadyExistsException"
    }

2) Authenticate (login)

- URL
  POST /api/v1/auth/authenticate

- Content-Type
  application/json

- Request body (JSON) — `AuthenticationRequest`
  Note: The `AuthenticationRequest` bean contains fields (fullName, email, password, phone) but only `email` and `password` are used by the authentication logic. Provide:
  - email: string — the user's email
  - password: string — the user's password

  Example
  {
    "email": "user@example.com",
    "password": "Secret123"
  }

- Success response
  - HTTP 200 OK
  - Body: `AuthenticationResponse`
    {
      "token": "<jwt-token-string>"
    }

- Error responses
  - HTTP 401 Unauthorized — Invalid credentials
    Body: `ErrorResponse`
    {
      "message": "Invalid email or password",
      "status": 401,
      "timestamp": "2026-03-17T12:34:56.789",
      "errorType": "InvalidCredentialsException"
    }

  - Note: There is no request-level validation on `AuthenticationRequest` in code, so malformed/missing fields will typically lead to authentication failure rather than a structured validation response.

Common response types
---------------------

ErrorResponse
- Fields
  - message: string — human-friendly error message
  - status: integer — HTTP status code
  - timestamp: string (ISO local date-time) — server time when error was created
  - errorType: string — one of the ErrorType enum values: `AccountAlreadyExistsException`, `InvalidCredentialsException`, `VALIDATION_ERROR`

ValidationErrorResponse
- Fields
  - timestamp: string — ISO local date-time
  - status: integer — HTTP status code (400)
  - errorType: `VALIDATION_ERROR`
  - message: string — brief message (e.g. "Request validation failed")
  - missingRequiredFields: array of field names that failed NotBlank/NotNull checks
  - fieldErrors: object mapping field name -> array of validation messages

Examples (curl)
---------------

Register (happy path)

curl -X POST "http://localhost:8080/api/v1/auth/register" \
  -H "Content-Type: application/json" \
  -d '{"fullName":"Jane Doe","email":"jane@example.com","password":"Secret1","phone":"4165551234"}'

Authenticate (happy path)

curl -X POST "http://localhost:8080/api/v1/auth/authenticate" \
  -H "Content-Type: application/json" \
  -d '{"email":"jane@example.com","password":"Secret1"}'

Notes & implementation details
------------------------------
- Registration checks for existing users by email and phone using `UserRepository.existsByEmail(...)` and `UserRepository.existsByPhone(...)`. If either exists, a 409 Conflict with ErrorType `AccountAlreadyExistsException` is returned.
- Passwords are stored encoded using the configured `PasswordEncoder`.
- Successful register/authenticate responses contain a token generated by `JwtService.generateToken(user)`. This token should be sent in the `Authorization` header for protected endpoints: `Authorization: Bearer <token>`.
- Validation for registration is implemented using Jakarta Validation annotations on `RegistrationRequest`. Validation failures produce `ValidationErrorResponse` via the `GlobalExceptionHandler`.

Change notes / assumptions
--------------------------
- The `AuthenticationRequest` DTO contains multiple fields but the authenticate flow uses only `email` and `password`; the docs reflect that.
- This document covers the controllers under `/api/v1/auth` only. Other endpoints (protected or otherwise) are not included here.
